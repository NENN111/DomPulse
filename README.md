# ДомПульс

MVP взаимодействия жителя и УК: чат-бот MAX, API обращений и надёжная очередь исходящих
сообщений. На своём ПК бот запускается через long polling; для сервера сохранён webhook.
Основной сценарий создания и просмотра обращений работает в диалоге с ботом,
без мини-приложения. Вложения и объединение похожих обращений — следующие этапы.

## Сценарий

Житель создаёт обращение об отоплении. Сотрудник УК своего дома принимает его,
отвечает, переводит в работу и сообщает об устранении. Житель подтверждает результат
либо сообщает, что проблема осталась. История событий сохраняется в SQLite.

Статусы: `new → accepted → in_progress → resolved → confirmed`.
Из `resolved` житель может выбрать `reopened`, затем УК возвращает его в `in_progress`.
`resolved` означает сообщение сотрудника о выполнении, а не подтверждённый жителем результат.
`accepted` — принятие в этом прототипе, не регистрация в сторонней системе УК/ГИС ЖКХ.

## Бот на своём ПК без Docker и домена (long polling)

Python 3.12, PowerShell. Один процесс получает события MAX, отправляет ответы из очереди
и проверяет просрочки. Отдельно запускать Uvicorn и `app.outbox` не нужно.

```powershell
cd D:\projects\ch\dompulse
# Создайте окружение, если его ещё нет:
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
if (!(Test-Path .env)) { Copy-Item .env.example .env }
notepad .env
```

Укажите `MAX_BOT_TOKEN` в `.env`. Остальные настройки имеют значения по умолчанию:
`DOMPULSE_DB=.local/dompulse.db`, `MAX_API_BASE=https://platform-api2.max.ru`.
`MAX_WEBHOOK_SECRET` для polling не требуется. Файл `.env` читается автоматически из
текущей папки; `--env-file путь` выбирает другой файл. Поддерживаются буквальные `KEY=value`,
необязательные кавычки вокруг значения и комментарии на отдельных строках. Переменные
окружения имеют приоритет; подстановка переменных и комментарии после значений не поддерживаются.

При первом запуске создайте тестовые дома и выпустите код привязки (seed повторять не нужно):

```powershell
.\.venv\Scripts\python -m app.seed --db .local/dompulse.db
.\.venv\Scripts\python -m app.enrollment --db .local/dompulse.db --house-id house-1 --role resident --ttl-hours 24
```

Если изменили `DOMPULSE_DB`, используйте тот же путь в `--db` у seed и enrollment.
Для второго аккаунта диспетчера выпустите отдельный код с `--role operator`.

Каждый последующий запуск — одна команда:

```powershell
.\.venv\Scripts\python -m app.polling
```

Дождитесь сообщения «Бот … запущен», затем отправьте ему в MAX `/код <полученный-код>`.
После привязки доступны `/start`, «Сообщить о проблеме» и «Мои обращения». Остановка — Ctrl+C.
Компьютер и процесс должны оставаться включёнными. Запускайте только один polling-процесс
для бота и не запускайте одновременно отдельный worker или webhook-сервер для этой базы.

Если у бота уже есть webhook-подписки, обычный запуск остановится с подсказкой. Для
явного переключения выполните команду ниже: она удалит **все webhook-подписки этого бота**,
поэтому прежний сервер перестанет получать события. Автоматического восстановления
подписок при остановке нет.

```powershell
.\.venv\Scripts\python -m app.polling --delete-webhooks
```

События обрабатываются теми же диалогами, что и webhook. Маркер следующего запроса
сохраняется в SQLite вместе с изменениями диалога и исходящими ответами; повторы
дедуплицируются. После перезапуска polling продолжает с сохранённого маркера. При самом
первом запуске без маркера MAX возвращает последнее обновление, а не всю историю.
Сетевые ошибки и ответы 429/5xx при опросе повторяются с задержкой до 30 секунд;
ошибки авторизации или запрет polling завершают процесс с сообщением об ошибке.

HTTPS-клиент использует системные доверенные сертификаты (включая хранилище Windows)
и публичный набор CA из certifi. Проверка сертификатов и имени сервера включена.
Если используется собственный CA, задайте `SSL_CERT_FILE` в переменных окружения PowerShell
как путь к PEM-файлу перед запуском. Явные `SSL_CERT_FILE`/`SSL_CERT_DIR` имеют приоритет;
из `.env` эти параметры не загружаются. TLS-ошибки, тайм-ауты и ошибки прокси показываются
отдельно, без вывода токена.

[MAX описывает long polling](https://dev.max.ru/docs-api/methods/GET/updates) как режим
для разработки и тестирования с ограниченным сроком хранения событий. Для production
сохранён запуск через webhook. Реальное подключение проверяется отдельно с токеном;
автотесты используют имитацию API MAX.

## Локальный запуск API (Python 3.12, PowerShell)

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
.\.venv\Scripts\python -m app.seed --db .local/dompulse.db
$env:DOMPULSE_DB = '.local/dompulse.db'
$env:MAX_WEBHOOK_SECRET = 'replace-with-a-long-random-secret'
.\.venv\Scripts\python -m uvicorn app.api:create_app --factory --host 127.0.0.1 --port 8080
```

Откройте http://127.0.0.1:8080/docs. `app.seed` создаёт два вымышленных дома,
двух жителей и двух сотрудников разных УК. Случайные Bearer-токены сохраняются только
локально в `.local/local-test-users.json`, в базе хранятся их хеши. Повторный seed существующих
пользователей запрещён. Не добавляйте базу, токены и файл пользователей в репозиторий.
Эта авторизация предназначена для локальной разработки. Не публикуйте прототип в интернет.

## Проверка через Swagger

1. В Authorize вставьте токен `resident-1` из локального файла (без префикса Bearer).
2. POST `/api/tickets`: category `heating`, location `Подъезд 1, квартира 12`,
   description `Со вчерашнего вечера холодные батареи`. Ожидается 201, id, status `new`, version 1.
3. Смените авторизацию на `operator-1`. GET `/api/tickets` показывает созданную карточку.
4. POST `/api/tickets/{id}/comments` с text добавляет ответ, видимый жителю.
5. POST `/api/tickets/{id}/status` переводит последовательно в `accepted`, `in_progress`, `resolved`.
   Передавайте `comment` и `expected_version` из последнего ответа/GET карточки.
6. Смените авторизацию на `resident-1`, подтвердите `confirmed` либо выберите `reopened`.
7. С токеном `resident-2` или `operator-2` чужая карточка возвращает 404 и отсутствует в списке.
8. Повторный запрос со старой версией возвращает 409; обновите карточку и повторите действие.

## Docker

```powershell
docker compose up --build -d
docker compose exec api python -m app.seed --db /data/dompulse.db
docker compose exec api cat /data/local-test-users.json
```

Последняя команда показывает секреты только в вашем терминале для теста. Не публикуйте вывод.
Порт привязан к 127.0.0.1:8080. Swagger `/docs`, OpenAPI `/openapi.json`, проверка `/health`.
Остановка: `docker compose down`. Повторный запуск: `docker compose up -d`.
Данные хранятся в именованном томе и переживают остановку. Повторять seed не нужно.

## Подключение MAX

1. Создайте `.env` по примеру `.env.example`. Не коммитьте этот файл.
2. Зарегистрируйте HTTPS webhook `https://ваш-домен/webhooks/max` с секретом из
   `MAX_WEBHOOK_SECRET`. Входящий секрет проверяется по заголовку
   `X-Max-Bot-Api-Secret` постоянным по времени сравнением.
3. На доверенной машине выпустите для пользователя одноразовый код из раздела «Привязка к дому».
   Затем он вводит в MAX `/код XXXX-XXXX-XXXX-XXXX` и проходит сценарий кнопками:
   «Сообщить о проблеме» → категория → место → описание → «Мои обращения».
   Диспетчер привязывается отдельным кодом с ролью `operator`, принимает обращения,
   устанавливает их срочность, ведёт статусы, получает группы похожих заявок и показатели дома.
   Житель получает уведомления и выбирает в MAX «Да, всё решено» либо «Проблема осталась».
   Сроки реакции: обычная заявка — 24 часа, срочная — 2 часа, авария — 15 минут.
4. Запустите API и обработчик исходящей очереди:

```powershell
docker compose --profile max up --build -d
```

## Привязка к дому

Сотрудник УК выпускает одноразовый код на доверенной машине, затем передаёт его конкретному
жителю или диспетчеру:

```powershell
.\.venv\Scripts\python -m app.enrollment --db .local/dompulse.db --house-id house-1 --role resident --ttl-hours 24
```

Пользователь вводит боту `/код XXXX-XXXX-XXXX-XXXX`. Код определяет дом и роль, имеет
срок действия и лимит использований. В webhook-логе вместо него сохраняется `[REDACTED]`;
после пяти неверных попыток привязка для MAX-пользователя блокируется на 15 минут. Сам
профиль MAX не является доказательством права на обслуживание в доме.

Webhook сначала сохраняет событие и ответ в одной транзакции, а затем немедленно
возвращает `200`. Повторная доставка одного `message.body.mid` не создаёт второе сообщение.
Отдельный worker отправляет очередь через `POST /messages?user_id=...`, передаёт токен
в `Authorization` и повторяет временно неудачные попытки с задержкой. Реальная отправка
MAX с настоящим токеном не проверена; публичный HTTPS-адрес требуется только для webhook.

## Архитектура и границы

- FastAPI + `asyncio`: обработчики API и webhook не блокируют цикл событий во время ожидания БД или MAX API.
- `aiosqlite`: неблокирующий доступ к SQLite; SQLite по-прежнему сериализует одновременные записи,
  поэтому для крупного пилота потребуется PostgreSQL.
- `app/db.py`: схема и транзакции. `app/models.py`: контракты. `app/api.py`: доступ и сценарий.
- `app/max_webhook.py`: проверка webhook, диалоговый сценарий, дедупликация и outbox.
- Внутри `app/max_webhook.py` группировка намеренно объяснимая: одинаковая категория плюс
  совпавшее место или заметное пересечение слов описания. Это рекомендация диспетчеру,
  а не автоматическое объединение и не заявление о применении ML.
- `app/sla.py`: расчёт демонстрационных сроков реакции и идемпотентный сканер просрочек.
- `app/analytics.py`: агрегированные показатели дома для диспетчера и `/api/metrics/house`.
- `app/enrollment.py`: выпуск ограниченных по времени кодов привязки к дому и роли.
- `app/max_api.py` и `app/outbox.py`: официальный HTTP-контракт MAX и повторная доставка.
- `app/polling.py`: локальный запуск, загрузка `.env`, long polling с сохранением маркера,
  общий worker отправки и явное переключение с webhook.
- Каждому пользователю назначен один дом и роль на сервере. Назначение дома из запроса запрещено.
- Житель видит только собственные обращения; сотрудник — обращения своего дома.
- Изменение статуса и событие записываются одной транзакцией. Проверка версии предотвращает
  перезапись нового состояния старым запросом.
- Личные данные соседей не публикуются. Общие обезличенные карточки появятся отдельным этапом.
- Данные seed полностью синтетические. Тесты MAX используют имитацию HTTP-ответа и явно
  не считаются подтверждением реального подключения.
- HTTP-токены пока не имеют срока действия/отзыва. Нет rate limiting, миграций схемы,
  загрузки файлов и production-развёртывания. При аварии worker после отправки, но до
  записи результата, возможна повторная отправка; перед production потребуется ключ
  идемпотентности или сверка результата. Публичная публикация требует этих доработок.
- Прямые зависимости закреплены. Полный lock зависимостей и проверка Docker-сборки
  на время до 5 минут нужны перед сдачей.

Проверка: `.\.venv\Scripts\python -m pytest -q`.
