# ДомПульс

ДомПульс — MVP для взаимодействия жителей многоквартирного дома и управляющей организации в MAX. Житель создаёт структурированное обращение, оператор ведёт его по прозрачному жизненному циклу, а повторяющиеся обращения могут быть подтверждены человеком как общедомовой инцидент.

## Проблема и ценность

Домовые чаты смешивают сообщения, повторения и обещания без контролируемого результата. ДомПульс превращает сообщение жителя в заявку с историей, ответственным контуром дома, SLA первой реакции и подтверждением результата самим жителем.

Целевая аудитория: жители МКД, диспетчеры УК/ТСЖ и руководители, которым нужны очередь, общие инциденты и измеримые показатели.

## As Is / To Be

- As Is: проблема теряется в чате, соседи дублируют сообщения, статус и результат неясны.
- To Be: заявка структурирована, похожесть объяснима, объединение подтверждается человеком, житель видит историю и принимает результат.

## Основной сценарий

1. Житель подтверждает адрес через подключённые Госуслуги либо вводит адрес вручную и подтверждает дом одноразовым кодом УК.
2. После привязки житель кнопками выбирает категорию, место и описание.
3. Бот показывает итоговую проверку; заявка создаётся только после «Отправить».
4. Если есть похожий активный подтверждённый инцидент, бот показывает только обезличенные категорию, место и срочность. Житель сам выбирает присоединение или отдельную заявку.
5. Оператор отвечает без смены статуса либо ведёт `new → accepted → in_progress → resolved`.
6. Житель подтверждает `confirmed` или возвращает `reopened`; оператор продолжает `reopened → in_progress`.

SLA — время до первой реакции УК. Реакцией считается принятие, ответ, изменение срочности/подтверждение инцидента или другое первое допустимое действие оператора. После заполнения `first_response_at` заявка не считается просроченной.

## Архитектура

```text
MAX webhook / long polling ─┐
                            ├─ диалог и бизнес-правила ─ SQLite
REST API ───────────────────┘              │
                                           └─ outbox ─ MAX API
```

FastAPI и MAX используют одну модель заявок. Входящее обновление, состояние диалога и исходящий ответ фиксируются транзакционно; `message.body.mid` дедуплицируется. Житель ограничен собственными заявками, оператор — своим домом. Подробности: [docs/architecture.md](docs/architecture.md).

## Структура

- `app/api.py` — REST API, роли и переходы статусов.
- `app/max_webhook.py` — webhook, диалоги, карточки, инциденты.
- `app/polling.py` — локальный long polling и сохранение marker.
- `app/outbox.py` — повторная доставка сообщений.
- `app/sla.py`, `app/analytics.py` — SLA и показатели.
- `app/db.py`, `app/models.py` — SQLite-схема и контракты.
- `tests/` — API, MAX, polling, безопасность и регрессии.
- `docs/`, `DATA-API.yaml`, `openapi.json` — материалы технической проверки.

## Быстрый локальный запуск MAX

Требуется Python 3.12+.

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
```

Заполните только локальный `.env`, затем один раз создайте синтетические данные и коды:

```powershell
.\.venv\Scripts\python -m app.seed --db .local/dompulse.db
.\.venv\Scripts\python -m app.enrollment --db .local/dompulse.db --house-id house-1 --role resident
.\.venv\Scripts\python -m app.enrollment --db .local/dompulse.db --house-id house-1 --role operator
```

Одна команда запуска:

```powershell
.\.venv\Scripts\python -m app.polling
```

Если у бота есть webhook, polling безопасно остановится. Явное переключение удаляет все webhook-подписки этого бота:

```powershell
.\.venv\Scripts\python -m app.polling --delete-webhooks
```

Не запускайте одновременно polling, webhook и отдельный outbox-worker для одной базы.

## MAX: polling и webhook

Polling предназначен для локальной разработки: marker сохраняется в SQLite, пакет обновлений и ответы коммитятся вместе, временные сетевые ошибки повторяются. Для demo/production используется `POST /webhooks/max` по HTTPS с обязательным `X-Max-Bot-Api-Secret`; ответы отправляет outbox-worker.

Токен передаётся MAX API только в `Authorization`. TLS-проверка и проверка имени сервера включены. При использовании собственного CA задайте `SSL_CERT_FILE` на PEM-бандл. Ошибки не выводят токен.

## Переменные окружения

- `DOMPULSE_DB` — путь к SQLite, локально `.local/dompulse.db`.
- `MAX_BOT_TOKEN` — секретный токен бота.
- `MAX_API_BASE` — обычно `https://platform-api2.max.ru`.
- `MAX_WEBHOOK_SECRET` — секрет входящего webhook; polling не требует.
- `GOSUSLUGI_BRIDGE_URL` — HTTPS-страница доверенного адаптера Госуслуг/ЕСИА; необязательно.
- `GOSUSLUGI_BRIDGE_SECRET` — общий секрет подписи callback, минимум 32 символа; необязательно.
- `SSL_CERT_FILE` / `SSL_CERT_DIR` — необязательное системное доверие CA, читается только из окружения.

`.env`, `.local/`, базы, тестовые токены и сертификаты не должны попадать в Git.

## REST API

Локальный запуск:

```powershell
$env:DOMPULSE_DB='.local/dompulse.db'
$env:MAX_WEBHOOK_SECRET='локальный-длинный-секрет'
.\.venv\Scripts\python -m uvicorn app.api:create_app --factory --host 127.0.0.1 --port 8080
```

Swagger: `http://127.0.0.1:8080/docs`, здоровье: `/health`. Bearer-токены для синтетических аккаунтов находятся только в `.local/local-test-users.json`. Проверки API описаны в [DATA-API.yaml](DATA-API.yaml), фактическая схема — [openapi.json](openapi.json).

Воспроизводимый экспорт:

```powershell
.\.venv\Scripts\python scripts/export_openapi.py
```

## Docker

```powershell
docker compose up --build -d
docker compose exec api python -m app.seed --db /data/dompulse.db
```


Тесты MAX используют имитацию HTTP-ответов, но проверяют фактические URL, заголовок авторизации, дедупликацию, marker, outbox, роли и отсутствие секретов в ошибках. Реальное подключение проверяется отдельно с токеном.

## Данные и интеграции

Seed создаёт только вымышленные дома и пользователей. Реальная интеграция — MAX Bot API. Для Госуслуг подготовлен защищённый bridge-контур: официальный OAuth/ЕСИА выполняет аттестованный внешний адаптер, а ДомПульс принимает минимальный набор подтверждённых адресных данных по HMAC-подписанному callback. Без настроенного bridge бот использует ручной адрес и одноразовый код УК. ГИС ЖКХ и внутренние системы УК не подключены и не имитируются.

Официальная документация подтверждает вложения `Message.body.attachments` и тип `image`. Таблица `ticket_attachments` подготовлена для метаданных, но приём фото выключен до подтверждения точной структуры входящего события на реальном боте; бинарные файлы не сохраняются. Подробнее: [docs/data-and-integrations.md](docs/data-and-integrations.md).

## Известные ограничения и масштабирование

Ограничения перечислены в [docs/known-limitations.md](docs/known-limitations.md). Следующие шаги: PostgreSQL и мигратор, отзыв токенов, REST rate limiting, наблюдаемость, защита outbox от повтора после неопределённого результата, пилот с УК и только затем минимальный MAX Mini App.

План Mini App после стабилизации backend:

- Resident: главная, мои обращения, карточка с timeline, общая проблема дома.
- Operator: очередь, общие инциденты, метрики.
- UI использует текущий REST API; роли и изоляция остаются серверными.

Чек-лист сдачи: [docs/submission-checklist.md](docs/submission-checklist.md).


## Округа Москвы для операторов

Домам и операторам можно назначить административные округа Москвы. Оператор видит заявки всех домов назначенных ему округов.

```powershell
.\.venv\Scripts\python -m app.operator_access --db .local/dompulse.db --house-id house-1 --district ЦАО
.\.venv\Scripts\python -m app.operator_access --db .local/dompulse.db --operator-id max-operator-123 --district ЦАО --district ЮАО
.\.venv\Scripts\python -m app.operator_access --db .local/dompulse.db --list
```

При авторизации оператора кодом его первичный округ наследуется автоматически.
